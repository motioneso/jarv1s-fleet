- Unit 2 (silence must never read as progress): DONE. Checks now come from the plain
  REST door first (old GraphQL-backed door only as fallback), a rate-limit answer is
  read as "GitHub refused to answer" and freezes nothing, a starved tick logs one
  fleet-level alarm instead of per-lane silence, and a lane stuck an hour with no
  record change and no log line raises a stillness alarm. All tests pass (`pnpm test`).
  Found and fixed one test-harness bug along the way: the `gh` stub used
  `${GH_CHECKS:-[]}`, which replaces an explicitly empty value with `[]` -- so tests
  that set `GH_CHECKS=''` to mean "no output" were silently getting a valid empty
  check list instead. Changed to `${GH_CHECKS-[]}` (no colon) so only a genuinely

- Unit 3 (lane recovery after first agent exits): DONE. Red checks and failed reviews
  now dispatch a deliberate, self-terminating fix agent into the lane's own worktree
  (brief carries the failing check names, or the reviewer's last PR comment as
  findings) instead of posting a comment nobody reads and waiting forever. Each cause
  (checks, review) gets at most two fix rounds, tracked in new record fields
  `ci_fix_rounds` and `qa_fix_rounds`; a third failure of the same kind parks the lane
  with a plain reason and lets the existing blocked-lane path file the question for
  Ben. The lane record gained a `reviewer` field so the QA agent's name no longer
  overwrites the builder's `agent` field (that overwrite was the accidental-respawn
  bug). The dead-agent check now also covers "in review": a reviewer gone 15 minutes
  is respawned once, a second death parks. The nightly spawn budget is now split: the
  last fifth is held back for recovery spawns only (fix agents, reviewer respawns), so
  a lane needing rescue is never starved by a busy night's ordinary work; if the whole
  budget (recovery included) is gone, the lane parks at once with reason "spawn budget
  exhausted" instead of waiting silently. Replaced the old ci-red two-strikes counting
  (which could never fire) and the old QA merge-or-park arbitration with this round
  counter, since both are superseded by the new fix-agent flow. All tests pass
  (`bash tests/test-fleet-tick.sh` and `pnpm test`). Live proof on a real PR still
  outstanding, same as prior units -- noted for later.
- Unit 4 (stop repeating model calls): DONE. Every judgment/deputy outcome now gets
  stamped on the lane record, so the daemon never asks a model the same question
  twice while nothing has changed. For the dead-lane check: a `judgment_attempts`
  counter on the record allows two retries when the model's answer does not parse;
  a third failure parks the lane with the model's own words in the parked reason
  instead of asking forever. For the deputy: new `deputy_reason` / `deputy_answer` /
  `deputy_attempts` fields remember what reason was asked about and what came back;
  the deputy is asked again only if the parked reason changes, and an unparseable
  deputy answer also gets two retries before giving up and updating the parked
  reason with the model's actual words. A lane parked for hitting the relay cap
  (needs re-slice) is no longer offered "put it back in the queue" as an option --
  only merge or stay parked, since re-slicing needs real judgment. Answer parsing
  is now more forgiving too: it accepts one of the allowed words appearing anywhere
  on the first line (not just as the first word), but two allowed words on the same
  line still counts as no answer, since guessing between them is worse than asking
  again. Added new fields to fleetctl.mjs's settable/int field lists and its default
  record shape. Test file's `claude` shim gained two things to make this testable:
  it now records the exact text it was asked (so a test can check an option like
  "put it back in the queue" was left out of the prompt) and can be fed a queue of
  answers, one per call, when a test needs to run several ticks with different
  answers each time. Nine new test cases cover: one deputy call per unchanged
  parked reason across many ticks, one more call permitted when the reason changes,
  three unparseable answers parking with the verbatim answer for both the deputy
  and the dead-lane check, no queue-option offered on a relay-capped lane, a
  prefaced answer like "I would RESTART" still parsing correctly, and two allowed
  words on one line still failing to parse. All tests pass (both
  `bash tests/test-fleet-tick.sh` and `pnpm test`). Live proof on a real parked
  lane over thirty minutes is still outstanding, same as prior units.
- Unit 5 (merges fail loudly or get out of the way): DONE. The auto-merge command's exit
  code is now checked instead of ignored. On failure the daemon reads the pull request's
  own merge-state answer and routes: branch merely behind main asks GitHub to update the
  branch and retries next tick (two failed update attempts park the lane, tracked in a new
  `merge_update_attempts` field); a real conflict spawns a fix agent using unit 3's
  machinery with a brief that says exactly "bring this branch up to date with main,
  resolve the conflicts, push" (counted in a new `merge_fix_rounds` field, same
  three-strikes pattern as the checks/review fix agents); anything else (auto-merge not
  allowed, rules refuse it) parks immediately with the command's own error text as the
  reason. Two new deadlines close off the open-ended waits: a lane stuck "merging" with
  the pull request still open for 45 minutes gets one merge-state re-check, routed the
  same way or parked with the state as the reason; a lane with checks pending for 90
  minutes gets one re-run request (asks GitHub to re-run the most recent workflow run,
  tracked in a new `checks_rerun_requested` field so it only happens once), waits another
  90 minutes, and parks with "checks never finished" if that also times out. Both
  deadlines are measured off the record's own `updated_at`, the same "remembering" pattern
  Unit 4 used, so accidentally re-triggering every tick is not a risk. Added the three new
  fields to fleetctl.mjs's settable/int/increment field lists and the default record
  shape. Test file's `gh` shim gained a `pr merge` case with a controllable exit code and
  stderr text, a `mergeStateStatus` answer for `pr view`, and `run list`/`run rerun` cases
  for the checks re-run request. Eight new test cases cover: a behind branch triggers
  update-branch and retries; two failed update attempts park the lane; a real conflict
  dispatches a fix agent with the rebase-and-push brief; a refused auto-merge parks with
  the command's own error text; merging past 45 minutes re-checks and routes (both to a
  mechanical fix and to a park); a lane still within the 45-minute window is left alone;
  pending checks past 90 minutes trigger exactly one re-run request; a second timeout
  after the re-run parks as "checks never finished". All tests pass (both
  `bash tests/test-fleet-tick.sh` and `pnpm test`). Live proof on a real PR (two lanes
  made to conflict on one file) is still outstanding, same as prior units -- not attempted.
- Unit 6 (close out on GitHub when done): DONE. When a lane's pull request is confirmed
  merged, the daemon now closes the GitHub issue (with a comment linking the merged pull
  request) and moves its project-board entry to Done before the lane record is allowed to
  move to done -- so the daemon's word "done" and the board Ben reads can no longer say
  different things. Both checks first (an already-closed issue or an already-Done board
  entry is one log line, nothing else) and both follow Unit 2's rules: a rate-limited
  answer backs off and retries next tick without counting as a failure, a genuine failure
  does count, and after three counted failures the lane is let through to done anyway with

  as done (`worktree` cleared to null) so a lane retrying its close-out does not repeat the
  worktree removal every tick while it waits. Parked/abandoned lanes are untouched by this
  -- the daemon never closes a parked lane's branch or pull request, that stays a human
  call. New record fields in fleetctl.mjs: `closeout_attempts` (int) and `closeout_note`
  (string, null unless the daemon gave up). The board (fleetctl.mjs's cmdBoard) gained two
  new sections: "Still open on GitHub", listing every lane marked done with a closeout
  note, and "Left behind", listing every parked lane's open branch and pull request. New
  gh calls added to tick.sh: `issue view --json state`, `issue close --comment`, `project
  view`, `project field-list`, `project item-edit`; the test file's gh shim gained matching
  cases. Five new dry-run-free (`run_tick_live`) test cases in tests/test-fleet-tick.sh

  being marked done; a failed close keeps the lane out of done and retries; the third
  failure marks done anyway with the note; an already-closed issue and an already-Done

- Unit 8 (lane watchdog, corrected): DONE. A new script, fleet-watchdog.sh, runs on
  its own one-minute systemd timer alongside tick.sh and watches every pane in the
  fleet's shared agents tab for a wedged lane. It maps panes to lanes with the same
  whole-token agent-name matching as Unit 7, so it can never mistake a pane for the
  wrong issue. A paused lane is skipped outright. "Signs of life" means the pane
  reports "working" or its content actually changed; "working" alone is never
  trusted on its own, because an agent stuck inside one endless tool call reports
  itself as working forever -- that is the most common way a lane wedges. Before a
  third strike is allowed to stop an agent, the watchdog looks at the real process
  under the pane (asking the terminal manager which process is on top, the same way
  Unit 7's spawn check does) and compares its total CPU time against the reading
  taken a minute ago. CPU that moved at all means "quiet but computing" -- logged,
  not stopped. If the process table can't be read, the pane's top process can't be
  found, or there is no earlier reading to compare against, the watchdog also does
  not stop anything -- it sends a nudge and logs that the check was unavailable,
  so a blind watchdog can never swing. The first two quiet periods (fifteen minutes
  each) just send a nudge into the pane; only the third, with CPU confirmed flat,
  stops the agent through the terminal manager and logs why, including the actual
  CPU numbers. One exception, ruled on directly by Ben and not to be revisited
  without a live incident: if a pane and its lane record have both gone three hours
  with no visible change at all, the watchdog stops it regardless of CPU, in case
  it is a genuine infinite loop rather than a slow-but-working agent. Nudge counts
  live in the watchdog's own small state file keyed by agent name, the same pattern
  as Unit 7's nightly spawn counter, and every nudge and stop is also written onto
  the lane's own record. New files: fleet-watchdog.sh, systemd/jarv1s-fleet-watchdog
  .service, systemd/jarv1s-fleet-watchdog.timer, tests/test-fleet-watchdog.sh.
  Changed files: launcher/src/operations.ts (the watchdog's service and timer are
  now installed and enabled alongside the tick ones, as their own unit so either can
  be turned off independently), launcher/test/self-check.ts, package.json (test
  script now also runs the new test file). Test coverage, all fixture-driven with no
  real agent ever wedged: CPU that grew between passes is never a kill and logs
  "quiet but computing"; CPU that stayed flat lets the third strike proceed; an
  unreadable process table, a pane whose top process can't be found, and a missing
  earlier CPU reading all fail safe the same way (nudge, logged as unavailable, no
  kill); a paused lane is never touched even when everything else says it's overdue
  for a stop; a pane with no fleet agent name is ignored; a lane quiet for three
  hours with CPU still climbing is stopped anyway by the backstop; a lane just
  going quiet gets its first nudge, not a stop; a second quiet period gets nudge two
  of two, still not a stop; and a pane reporting "working" resets the clock. All
  eleven pass (`bash tests/test-fleet-watchdog.sh`), and so do the full suites
  (`bash tests/test-fleet-tick.sh` and `pnpm test`, which now also runs the
  watchdog tests). Live proof -- actually wedging a real agent and watching the
  watchdog nudge then stop it -- is still outstanding, same as prior units, not
  attempted per instructions.
- Unit 9 (viewer): DONE. The launcher now reads real token spend instead of showing nothing,
  and can end a run cleanly from the keyboard. New file launcher/src/tokens.ts finds a lane's
  own Claude session transcripts by working out the same folder name the Claude program itself
  writes them under (every "/" and "." in the lane's worktree path becomes "-", the same
  scheme confirmed by looking at real transcripts on this machine), sums the usage record on
  each line, and remembers in a small per-lane sidecar file (state directory's new
  token-usage/<issue>.json) both the offset it last read to (so a refresh only reads bytes
  appended since last time, not the whole file) and every session file path it has ever seen
  for that lane, so a relay's second session or a fix agent's own session still counts instead
  of quietly replacing the first one's spend. A lane is only summed at all if the program
  configured to build its tier is "claude" -- any other program shows "not reported" in the
  viewer, never a zero, since a zero there would read as free. Fresh tokens (input plus what
  got newly cached) are shown separately from cache reads, which are usually two orders of
  magnitude bigger and would swamp the number otherwise. The viewer's header now shows the run
  clock, a live/stopped/ended indicator, lanes in progress against the cap, agent starts used
  against tonight's budget, how many lanes are waiting on Ben, the deputy's on/off state, and
  the token total underneath (caption: "tokens this run, Claude lanes only"). Each in-progress
  lane now prints three lines: what it is, a text token bar plus its own token label, and one
  plain sentence describing where it actually stands (e.g. "Merging now." or "A check is
  failing: build."); a lane waiting on Ben collapses to one dim line instead, since there is
  nothing more to watch happen until he answers. The former "Done Tonight" tab is renamed
  "Completed This Run" per Ben's ruling and is the last of the three tabs. Colour marks status
  throughout (yellow for waiting on Ben, red for a failing check or review, green for merging
  or a passed review, grey once done). New key: "e" asks to end the run (confirmed with y/n),
  then asks whether to leave running agents working or close their panes; either way it stops

  Completed This Run freezes at whatever actually finished by then instead of continuing to
  fill in afterwards, and rotates the log. Log rotation needed one small addition to
  fleetctl.mjs: a new "rotate-log" command that forces the same rename-to-.1 rotation the
  existing 10 MB cap already does, since ending a run should not have to wait for the log to
  grow that large on its own -- this reuses the exact same rotation code Unit 7 wrote, just
  callable on demand. Starting a run (from Setup or the "press s to start" prompt) now also
  clears any leftover run-ended stamp from a previous run first, so restarting the fleet after
  ending it does not make the new run look instantly finished. Changed files: launcher/src/
  tokens.ts (new), launcher/src/view.tsx, launcher/src/state.ts (writeRunEnded/clearRunEnded/
  readRunEnded, runEnded added to LoadResult), launcher/src/operations.ts

  non-Claude lane's tier excluded from the Claude-only fleet total, Completed This Run freezing

  units with disable and --now; the existing guard that no model name leaks outside the seed

  tests/test-fleet-tick.sh`, `bash tests/test-fleet-watchdog.sh`, and `pnpm test` from the repo
